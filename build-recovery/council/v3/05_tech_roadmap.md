### 1.2 طبقات الجودة المقترحة (Quality Tiers)

ثلاث طبقات في `QualitySettings` + أصل URP منفصل لكل طبقة، يُختار تلقائياً عند أول تشغيل (قياس GPU/RAM + benchmark قصير 5 ث)، ويمكن للاعب تغييره.

| البند | **Low** (A16 وما يشبهه) | **Medium** (Android متوسط 2023+) | **High** (iPhone 15 Pro/16 Pro، Galaxy S24+) |
|---|---|---|---|
| هدف الإطار — المعركة | **30 fps ثابت** (33.3 ms) | 60 fps (30 مع البطارية المنخفضة) | **60 fps**، خيار 120 للمعركة فقط |
| هدف الإطار — الخريطة (Mapbox) | 30 fps، وينزل إلى 20 في الخمول | 30 | 60 |
| Render Scale | 0.70–0.75 | 0.85 | 1.0 (أو STP upscaling من 0.8) |
| MSAA | Off (أو FXAA) | 2× | 4× (رخيص على TBDR) |
| HDR / Post | HDR off، **لا post** (tonemapping في shader) | HDR، ACES + Bloom خفيف | ACES + Bloom + Color grading LUT + Vignette |
| الظلال | بطل واحد: Shadow map 512، cascade واحد، مسافة 15 م؛ أو blob shadow | 1024، cascade واحد | 2048، 2 cascades، soft shadows |
| الإضاءة | Directional واحد realtime + lightmaps + light probes | نفسه | نفسه + Additional lights (≤4 per object) |
| SSAO / Decals / Volumetrics | لا | لا | SSAO منخفض للمعركة فقط (يُقاس) |
| حدّ المثلثات في الإطار (المعركة) | ≤ 150k | ≤ 250k | ≤ 500k |
| Draw calls / SetPass | ≤ 100 / ≤ 40 (SRP Batcher on) | ≤ 150 | ≤ 250 |
| Skin weights | 2 bones/vertex | 4 | 4 |
| القوام (Global Mipmap Limit) | 1 (نصف الدقة) | 0 مع ASTC 6×6 | 0 مع ASTC 4×4 للبطل |
| Texture memory budget | ≤ 300 MB | ≤ 500 MB | ≤ 1 GB |
| LOD Bias | 0.6 | 1.0 | 1.5 |
| الشعر | hair cards قليلة alpha-clip | أكثف | أكثف + anisotropic spec |
| الجلد | Lit + smoothness map | + pre-integrated wrap lighting | + detail normal + pre-integrated SSS تقريبي (لا SSS حقيقي) |
| القماش | سلاسل عظام 4–5 (لا محاكاة) | نفسه | + Spring bones أنعم |

**قواعد لكل الطبقات:** SRP Batcher on؛ GPU instancing لعلامات الخريطة؛ لا Realtime GI؛ لا شفافية إلا زجاج الخوذة؛ Shader variants مقلّمة (Shader stripping) لتقليل وقت التحميل؛ ASTC على Android وiOS.

### 2.1 الواقع: ماذا تعطي أدوات Image-to-3D اليوم

لدينا في `scratchpad/council/art/gemini/` لوحات بورتريه وturnaround للأبطال الثلاثة وأسلحتهم.

| الأداة (2026) | ما تعطيه | الترخيص/التكلفة التقريبية | ملاحظة |
|---|---|---|---|
| Meshy (6.x) | شبكة كثيفة + قوام ملوَّن، أحياناً auto-rig بسيط | اشتراك ~US$20–60/شهر؛ الخطط المدفوعة تسمح بالاستعمال التجاري | جيد للدروع والإكسسوارات؛ الوجوه واليدان ضعيفة |
| Tripo (v2.5/v3) | شبكة أنظف نسبياً، خيار quad، auto-rig | ~US$20–50/شهر | الأفضل غالباً للطوبولوجيا بين الخدمات |
| Rodin (Hyper3D Gen-2) | تفاصيل عالية، PBR منفصل | ~US$30–100/شهر | جيد للمسودات عالية الدقة (high-poly للـbake) |
| Microsoft TRELLIS (مفتوح، MIT) | محلي على GPU قوي | مجاني؛ يحتاج GPU ≥ 16 GB VRAM أو سحابة | بلا قيود ترخيص |
| Hunyuan3D (Tencent) | جودة قوية | **ترخيصه يستثني الاتحاد الأوروبي والمملكة المتحدة وكوريا الجنوبية** | **مستبعد**: صاحب المشروع في ألمانيا |

**النتيجة الصادقة:** الناتج من صورة واحدة/turnaround هو **«تمثال» مثلّثات كثيف** (100k–1M)، ظلال مخبوزة في القوام، يدان وأصابع مدموجة، وطوبولوجيا لا تنثني جيداً عند المفاصل. **لا يصلح مباشرة لشخصية تُحرَّك**. يصلح: (أ) مسودة حجم (blockout) يعتمدها الفنان، (ب) high-poly للأسلحة والدروع يُخبز على low-poly، (ج) قطع ثابتة (props، أعمدة المشربية، صناديق الغنائم).

| Rokoko Smartsuit (عتاد) | mocap كامل | US$2.5–4k+ | 9/10 — **غير مقترح الآن** |

**خط مقترح للحركات:** Mixamo للحركة الأساسية (Alpha) ← تصوير صاحب المشروع أو ممثل محلي بهاتف ← Rokoko Vision/Move.ai ← تنظيف وضبط إطارات التلامس في **Cascadeur** حسب أوقات الـwind-up المعتمدة (`art_bible_v2` §6: Pulse Blade 0.20 ث، Titan Hammer 0.55 ث، …). الحركات Humanoid بـ30 fps، root motion off (الحركة يقرّرها الـhost/الخادم، الحركة شكلية فقط).

**تنبيه معماري:** لا يوجد Animator في الكود. ربط الحركات **نظام جديد** يحتاج موافقة. التصميم المقترح له: Animator يقرأ فقط الحالة الشبكية (`NetworkedState`/`ActionBits` المؤكَّدة + سرعة الحركة)، **ولا يقرّر شيئاً** (لا animation events تُطلق ضرراً). الضرر يبقى في `PlayerCombat` على الـhost/الخادم.

## 3. الشبكة لقتال أعمق (Photon Fusion 2.0.13)

### 3.1 الوضع الحالي (من الكود و`council/unity.md`)

| العنصر | الحالة |
|---|---|
| النمط | Host Mode، المهاجم هو Host (`GameMode.Host`)، المدافع Client |
| Tick | 64 Hz (`NetworkProjectConfig.fusion`)؛ ConnectionTimeout 10 ث |
| القتال | يجري على الـhost فقط (`HasStateAuthority && Runner.IsForward`)؛ الإدخال `NetworkInputData` (محاور + `ActionBits`) |
| التنبؤ | **لا prediction** لحركة العميل ولا لحركاته؛ `Render()` بلا interpolation (snap) |
| النتيجة | الـhost يوقّع بـHMAC (`host_authority_secret`) ويرسل `/resolve`؛ الخادم يفحص المعقولية |
| الثغرات المقبولة لـAlpha | الـhost يستطيع توقيع أي نتيجة؛ ميزة 0 ms للـhost؛ لا rejoin؛ خروج اللاعب يمحو الخسارة (backend H3) |

### 3.2 ما يحتاجه قتال أعمق (combat_v2: حتى KO، 180+120 ث، wind-up، dodge بـi-frames)

| التقنية | لماذا | كيف في Fusion 2 | الجهد |
|---|---|---|---|
| **Client-side prediction للحركة** | الحركة فورية على شاشة اللاعب رغم RTT 60–150 ms | تحريك في `FixedUpdateNetwork` لكل من InputAuthority وStateAuthority، باستعمال **Simple KCC / Advanced KCC addon** من Photon أو NetworkCharacterController؛ الـresimulation تصحّح | M (2–3 أسابيع) |
| **Interpolation للخصم** | إزالة الارتعاش (L1) | `NetworkTransform` أو interpolation يدوية في `Render()` من snapshot buffer | S |
| **تنبؤ شكلي للحركات** | الضغطة تشغّل حركة الضرب فوراً محلياً | animation + VFX محلياً عند الضغط؛ **الضرر فقط من الـauthority** | S–M (بعد نظام Animator) |
| **Lag compensation** | الضربة تُحكم على ما رآه المهاجم وقت الضغط | `HitboxRoot`/`Hitbox` على الأبطال + `Runner.LagCompensation.Raycast/OverlapSphere` على الـauthority بالـtick الخاص بالإدخال؛ حدّ أقصى للتعويض ~200 ms لمنع «ضُربت خلف الجدار» | M |
| **Dodge i-frames عادلة** | i-frames 0.2 ث أقل من RTT أحياناً | نافذة i-frames تُقيَّم في tick الإدخال (مع lag comp)، لا وقت الوصول | S |
| Cooldowns مشتركة | حالياً العميل يرى «جاهز» دائماً | `[Networked]` TickTimer لكل قدرة | S |
| Rejoin | قفل الشاشة يُنهي المعركة (L10) | ConnectionTimeout > grace الخادم، وrejoin بنفس `SessionName` + `PlayerRef` مخزَّن؛ أسهل كثيراً في Server Mode | M |

### 3.3 مشكلة الـHost الغشاش: الخيارات

| الخيار | ما يحلّه | ما لا يحلّه | التكلفة الشهرية التقريبية | الجهد | التوصية |
|---|---|---|---|---|---|
| **0. Host Mode الحالي + فحوص معقولية** | لا شيء جوهري؛ يرفع صعوبة الغش قليلاً | الـhost يقرّر كل شيء | Photon CCU فقط | 0 | **Alpha فقط** (قرار 2026-10-19) |
| 1. Host Mode + سجل إدخالات يُعاد محاكاته في الخادم (replay validation) | يكشف النتائج المزوَّرة لاحقاً | فيزياء Unity غير حتمية؛ صيانة محاكاة مزدوجة (C# وJS)؛ الغش اللحظي (تعديل الضرر) صعب الإثبات | منخفضة | L، وهش | **لا** |
| **2. Fusion Server Mode على خادم مخصّص headless (المقترح لـBeta)** | الخادم وحده StateAuthority ويملك سر التوقيع؛ لا ميزة latency لطرف؛ rejoin ممكن؛ مشاهدة (spectator) للبطولات والمؤثرين ممكنة | bots/macros على العميل (يكافَح بـPlay Integrity/App Attest وفحص الإدخال) | انظر 3.4 | M–L (4–6 أسابيع): Linux Dedicated Server build، `GameMode.Server`، خدمة تخصيص (allocation) تُطلق خادماً لكل معركة، والخادم الخلفي يعطي السر للخادم المخصّص لا للهاتف | **نعم، قبل أي بطولة بجوائز** |
| 3. Shared Mode | — | لا سلطة لأحد؛ أسوأ للغش | — | — | لا |
| 4. محاكاة قتال كاملة في Node | سلطة كاملة | إعادة كتابة نظام معتمد (ممنوع)؛ 64 Hz في Node لكل معركة | — | XL | لا |

**لماذا Server Mode هو الأقل تغييراً:** كود Fusion الحالي مبني أصلاً على «السلطة تحسب، العميل يرسل الإدخال» (`HasStateAuthority`)، فيصبح الـhost خادماً بلا لاعب محلي. التغييرات: لا avatar محلي على الخادم، `IsOnHostMachine` يصبح false للطرفين، و`/resolve` يُرسل من الخادم المخصّص بمفتاح خادم-إلى-خادم. هذا **تحويل سلطة** وليس إعادة تصميم للقتال، لكنه يغيّر عقد `/battle/challenge` (لا يعود السر للمهاجم) — يحتاج موافقة وتحديث `tests/contract`.

### 3.4 تكلفة الخوادم المخصّصة

افتراض: معركة 1v1 بـ64 Hz على Unity headless (`-batchmode -nographics`، Server build، أصول مقلّمة) ≈ 0.1–0.2 vCPU و150–300 MB RAM؛ متوسط المعركة 3–5 دقائق.

| المقياس | 10k DAU | 100k DAU |

| Peak CCU (≈10% من DAU) | ~1,000 | ~10,000 |

| VMs مخصّصة (8 vCPU، ~30–40 معركة لكل VM)، منطقة واحدة | 2–3 VMs | 15–25 VMs |
| **خيار A: VMs خاصة** (Hetzner/OVH وما يماثلها) مع orchestration بسيط (خدمة Node تُشغّل عمليات) | ~US$100–250/شهر | ~US$1,000–2,500/شهر |

| Photon Fusion CCU (الخادم المخصّص يُحسب CCU أيضاً — يُتحقَّق) | خطة 500–1,000 CCU: ~US$100–200/شهر | 5k–10k CCU: ~US$800–2,000/شهر (تفاوض) |

**قيد تقني:** Mapbox وFirebase لا يلزمان على الخادم المخصّص؛ يجب أن يُبنى Server build بـdefines تستبعدهما (البنية الحالية بـscripting-define guards تساعد هنا).

## 4. الخادم الخلفي للبطولات العالمية ولوحات الصدارة والسفر

### 4.1 الحمل الحالي المتوقَّع من التصميم الحالي

كل لاعب على MainMap يرسل: PATCH موقع كل 5 ث، `GET /player/nearby` كل ~6 ث، `GET /battle/incoming` كل 5 ث ⇒ **≈0.57 طلب/ث لكل لاعب متصل**.

| | 1k CCU (≈10k DAU) | 10k CCU (≈100k DAU) |
|---|---|---|

الافتراضات: صاحب المشروع + Claude، **+ فريلانسر 3D بدوام جزئي من Beta، + مستشار قانوني للخصوصية بالساعة، + اختياري: مطوّر Unity/شبكات بدوام جزئي لـServer Mode**. الجهد بـ«أسابيع-شخص» (pw) لصاحب المشروع مع مساعدة AI. التواريخ تقديرية من 2026-11.

## 8. القرارات المطلوبة من صاحب المشروع (ملخص)

1. اعتماد تعريف «الواقعية» = شبه واقعي سينمائي بثلاث طبقات (30 fps على A16، 60 على iPhone 16 Pro).
2. مسار الشخصيات: هجين (CC4 + AI للإكسسوارات) لـAlpha/Beta، ثم تكليف للإطلاق؛ ميزانية تقريبية US$1–4k ثم US$11–30k.
3. اعتماد Animator كنظام جديد (عرض فقط، بلا قرار ضرر).
4. السيلفي: الخيار 1 (مُعامِلات على الجهاز، لا رفع للصورة)، 18+، حجب BIPA، DPIA ورأي قانوني قبل البناء؛ وقرار ما بعد انتهاء الاشتراك.
5. الانتقال إلى Fusion Server Mode + خوادم مخصّصة في Beta، وتغيير عقد `/battle/challenge` (السر لا يذهب للهاتف).
6. لا مسابقات بجوائز قبل Server Mode وPlay Integrity/App Attest.
7. بنية الخادم: خادم مستضاف HTTPS في Alpha، Redis + WebSocket في Beta، منطقة واحدة في الشرق الأوسط حتى ~100k DAU.
8. iOS عبر Codemagic + TestFlight، وشراء/استعارة iPhone للاختبار.
9. توقيت الإطلاق: soft launch خريف 2027 (لا صيف الخليج)، وجدول الـ14 مسابقة.
10. السفر الافتراضي يتطلب قرار GDD بشأن قاعدة الـ20 م للمعركة داخل المدينة الافتراضية.
